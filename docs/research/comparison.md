# Cross-platform comparison

| Platform | Language | License (OSS repo) | Self-host full stack? | Auth model shape | Auth schemes beyond OAuth2? | Refresh strategy | Trigger model | MCP-native? |
|---|---|---|---|---|---|---|---|---|
| **Pipedream** | JS/TS (components), backend closed | "Other" (NOASSERTION) | No — component lib only, orchestration is SaaS | Platform-injected `$auth` token into component calls | Yes (API key components exist) | Not visible (closed backend) | Per-trigger-instance: `$.interface.http` (webhook) or `$.interface.timer` (poll), with `$.service.db` for cursor/dedupe state | Retrofitted (component shape doubles as MCP tool schema) |
| **Composio** | TS/Python SDK, backend closed | MIT | No — SDK only, execution is SaaS | Auth Config (how) + Connected Account (per-user credential), per-`userID` from the ground up | Yes (`AuthScheme.ts` typed union: OAuth2, API key, basic, etc.) | Automatic, invisible to caller (backend-owned) | One signed webhook URL per project, fans in all trigger instances; WebSocket `subscribe()` for prototyping | Yes — has `MCP.ts`, `ToolRouter.ts` |
| **n8n** | TypeScript | Sustainable Use / Fair-code (source-available, not OSI) | Yes (full engine is in the repo) | Declarative `ICredentialType` schema; project/role-scoped sharing (RBAC) | Yes (any credential type a node author defines) | Own OAuth2 client lib (`@n8n/client-oauth2`); server-side proxy for code exchange | Node-based: webhook nodes (`webhook.service.ts`) or poll nodes with staged-cursor commit | Retrofitted (MCP trigger + OAuth-resource-server surface added recently) |
| **Nango** | TypeScript | "Other" (verify; historically Elastic 2.0) | Yes (full connection-mgmt layer is in the repo) | "Connection" entity per user+provider; declarative provider registry (400+) | Yes (OAuth2, JWT, AWS SigV4, GitHub App, HMAC/signature, assertion) | **Proactive**, refresh-ahead-of-expiry margin + explicit failure state machine (`refresh_exhausted`) | Thin — "Syncs" (poll/ELT) + outbound signed webhooks to Nango's own customers; no inbound third-party-webhook trigger engine | Retrofitted (`mcp/connections` controllers appearing) |
| **Airbyte** | Java/Kotlin + Python CDK | MIT (core) + ELv2 (some connectors) | Yes | Two-tier: platform-managed shared OAuth app vs. bring-your-own-app override at workspace/org level | Yes (API key, PAT, OAuth) | Platform auto-rotates using stored refresh token | None comparable — "trigger" = sync schedule (cron), not event-driven | No (data-sync schema, not tool schema) |
| **Zapier** | JS/TS (CLI/SDK only) | MIT (SDK only; runtime closed) | No — only the dev-time SDK is open | `authentication` config block: custom/basic/digest/oauth1/oauth2/session | Yes | Declared by integration author (`refreshAccessToken`); executed on closed infra | Polling (`perform` on schedule) or REST hook (`performSubscribe`/`performUnsubscribe`) — both executed on closed infra | No (own `inputFields`/`display`/`sample` format, close in shape) |
| **Activepieces** | TypeScript, Bun-compatible | MIT (CE) | Yes | Per-piece TS auth definitions (OAuth2/API key/custom), no central declarative config | Yes | Per-piece, implemented in TS by the piece author | Dual: webhook or polling, declared per-piece alongside its actions | **Yes — auto-generates MCP servers from pieces** |
| **Windmill** | Rust (engine) + multi-lang scripts | AGPLv3 | Yes | Centralized "Resources": typed, pre-built credential templates (60+), encrypted, referenced by scripts | Yes (any resource type) | Not deep-dived yet (flagged in open-questions.md) | Webhook (auto-generated URL per script/flow) or schedule (cron); no distinct polling-trigger abstraction | No (script signature inferred, not MCP-native) |
| **Klavis AI** | Not deep-dived at file level yet | MIT | Dual (self-host components + managed) | Two-party OAuth split (platform-developer creds vs. end-user creds), same shape as Nango/Airbyte | Unclear yet | Not documented in sources reviewed | **Unclear/unconfirmed** — may be purely synchronous tool-calling with no trigger system (open question) | **Yes — native MCP servers per integration, closest target-format match** |

## Reading the matrix

- **Auth-first shortlist**: Nango (auth-only depth), Composio (multi-tenant model), n8n (declarative schema + encryption service), Windmill (centralized Resources) — these four should drive the auth-layer design most.
- **Trigger-design fork**: per-trigger-instance endpoint (Pipedream/n8n/Activepieces) vs. single fan-in webhook per consumer (Composio) vs. thin/absent (Nango/Klavis/Airbyte). No consensus — this is a real design decision, not a "just copy the winner" situation. See `triggers-patterns.md`.
- **Closest full-shape precedent**: Activepieces (TS + Bun + MCP-native + full self-hostable stack) is the only platform that is simultaneously same-language, same-runtime-option, and already doing MCP generation from integration definitions.
- **Closest protocol-target precedent**: Klavis (MCP-native tool schemas from the start, not retrofitted).
