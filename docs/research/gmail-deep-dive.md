# Gmail integration deep-dive: auth + trigger across platforms

Targeted follow-up to the main survey (see `README.md`, `platforms/*.md`), focused on how each platform actually implements a Gmail "new email" trigger and Gmail OAuth, since Gmail is the first integration planned for the from-scratch TS/Bun build. All findings below are read from live source (GitHub API / raw files), not docs alone, except Composio (closed backend — docs only).

## Pipedream — `components/gmail/`

- **Files**: `gmail.app.mjs` (auth/client), `sources/new-email-received/new-email-received.mjs`, `sources/common/polling-history.mjs`, `sources/common/base.mjs`, `sources/common/verify-client-id.mjs`, plus 4 more trigger variants (`new-attachment-received`, `new-email-matching-search`, `new-labeled-email`, `new-sent-email`) sharing the same common code.
- **Mode**: **hybrid, user-selectable** — a `triggerType` prop lets the user pick `polling` (default) or `webhook` (instant, via Gmail push notifications). Webhook mode requires a **custom OAuth client** (not Pipedream's shared one) plus a GCP service account with **Pub/Sub Admin** permission, entered as a pasted JSON key — the component walks the user through creating/selecting a Pub/Sub topic (`topicType`, `topic` props) for Gmail's `users.watch()` to publish to.
- **Polling implementation is not naive timestamp polling** — it's the correct Gmail-recommended pattern: store a `historyId` cursor (`db.get("lastHistoryId")`), call `users.history.list({ startHistoryId })` to get only the delta since last poll, and explicitly handle the case where the stored `historyId` has expired (Gmail retains history for a limited window) by catching the 404 and reseeding from `users.getProfile()`. This is meaningfully more robust than a `messages.list` + `after:<timestamp>` approach (see n8n/Activepieces below) — timestamp queries can miss messages with clock skew or miss/duplicate at poll-interval boundaries; `historyId`-based delta fetch is what Google's own docs recommend for this reason.
- **Complexity**: **medium-large** for the full dual-mode implementation (~5 source files + shared history/dedup/verify-client-id helpers), but the **polling-only path alone is small-medium** (`polling-history.mjs` is ~150 lines) and directly portable as a pattern.
- **OAuth**: standard Google OAuth2, scopes not hardcoded in the file reviewed (declared via `gmail.app.mjs`, typically `gmail.readonly`/`gmail.modify` depending on action).

## Composio — Gmail toolkit (closed backend, docs-only)

- Source not inspectable (SaaS execution backend); per `docs.composio.dev/toolkits/gmail`: **2 Gmail triggers** exist. Explicit FAQ quote: *"Gmail triggers poll roughly every minute by default. If you need lower latency, consider using webhooks or Google Pub/Sub integrations."*
- **Mode**: **polling by default** (~60s interval), Pub/Sub available as an opt-in for lower latency — same hybrid philosophy as Pipedream, but the default leans toward simplicity over latency.
- **OAuth scopes referenced in docs**: `gmail.readonly`, `gmail.modify`, `gmail.settings.basic`, `gmail.metadata`, `mail.google.com` (custom scopes supported when bringing your own OAuth app).
- **Complexity**: not assessable (no implementation visible) — this only confirms the *product decision* (poll-by-default, Pub/Sub optional), not an implementation reference.

## n8n — `packages/nodes-base/nodes/Google/Gmail/`

- **Files**: `GmailTrigger.node.ts`, `Gmail.node.ts` (actions), `GenericFunctions.ts`, `types.ts`, `test/GmailTrigger.test.ts`.
- **Mode**: **polling only**, no Pub/Sub option. Implements `IPollFunctions`, using `gmail.users.messages.list` filtered by query (e.g. unread + label filters), not `history.list`/`historyId`.
- **Notably nontrivial despite being "just polling"**: the file defines explicit tuning constants — `MAX_SCAN_PAGES = 20` (caps pages scanned per poll), `MAX_TRACKED_BACKLOG_IDS = 5_000` (backlog-size cutoff before the poll gives up tracking precisely), `MAX_PENDING_FETCH_ATTEMPTS = 10` (retries for a message id that failed to fetch), `MAX_NO_PROGRESS_TICKS = 3` (a "no new mail found N times in a row" give-up valve). This is a real signal: **getting exactly-once-ish Gmail polling right requires this much bookkeeping even without Pub/Sub** — worth treating as a checklist of edge cases (partial-page failures, indistinguishable rate-limit-vs-real-failure, backlog blowup) rather than copying the code.
- **Auth**: `gmailOAuth2` credential (n8n's Google-OAuth2-flavored credential type) for OAuth, or a `googleApi` service-account credential — same two-mode auth split seen in Activepieces below.
- **Complexity**: **medium** — single trigger file but with meaningful polling-correctness logic (~250+ lines including the constants/backlog handling), plus a dedicated test file.

## Activepieces — `packages/pieces/community/gmail/src/lib/`

- **Files**: `auth.ts`, `triggers/new-email.ts` (+ `new-attachment.ts`, `new-conversation.ts`, `new-label.ts`, `new-labeled-email.ts`), `common/props.ts`, `common/models.ts`, `common/data.ts`.
- **Mode**: **polling only** (`TriggerStrategy.POLLING`), simplest implementation of the three polling examples. Stores a single `lastPoll` epoch-ms timestamp in `context.store`, queries `gmail.users.messages.list` with an `after:<unixSeconds>` filter (plus optional from/to/subject/label/category filters), processes oldest-first, and advances the cursor to `max(epochMilliSeconds)` of the returned batch.
- No `historyId`/delta-fetch, no backlog/no-progress bookkeeping like n8n — trades some correctness robustness for much less code. First poll defaults to fetching the 5 most recent messages (`maxResults = lastFetchEpochMS === 0 ? 5 : 20`).
- **Auth**: dual — `PieceAuth.OAuth2` (standard, scopes: `gmail.send`, `gmail.readonly`, `gmail.compose`, `gmail.modify`, `email`) or `PieceAuth.CustomAuth` for a service account + domain-wide-delegation flow (JSON key + impersonated user email), with a `validate()` callback that test-fetches a token before accepting the connection.
- **Complexity**: **small** — the trigger file itself is ~150 lines including the polling helper function; this is the leanest working "new email" trigger implementation found in the survey, and it's TypeScript, matching the planned stack.

## Klavis — `mcp_servers/gmail/`

- **Files**: `src/index.ts` (single file, MCP server), `src/utl.ts` (attachment/PDF/DOCX/XLSX text extraction helpers), `package.json`.
- **Mode**: **no trigger mechanism at all.** This is a pure request/response MCP tool server: `send_email`, `read_email` (`ReadEmailSchema`), `search_emails`, `modify_email` (labels), `delete_email`, plus contact search — all synchronous tool calls, zero polling/webhook/watch code anywhere in the file.
- **Auth**: does not implement an OAuth flow itself — `extractAccessToken()` reads a pre-obtained access token either from an `AUTH_DATA` env var or an `x-auth-data` request header (base64-encoded JSON containing `access_token`). OAuth acquisition is delegated entirely to Klavis's separate platform-level OAuth service (`docs/oauth/gmail-oauth.mdx`) — this server only *consumes* a token, it doesn't manage refresh/storage.
- **Stack**: TypeScript, `@modelcontextprotocol/sdk` (official MCP SDK) + `googleapis` (official Google API client) + `zod`/`zod-to-json-schema` for tool schemas + `express` for the HTTP transport. Dependencies: 8 runtime (`@modelcontextprotocol/sdk`, `googleapis`, `zod`, `zod-to-json-schema`, `express`, `pdfjs-dist`, `mammoth`, `exceljs`) + 3 dev.
- **Complexity**: **small** for the MCP tool-calling surface (one ~400-line `index.ts` file handles all 6+ tools), but this is because it deliberately has **zero trigger complexity** — it's the cheapest of the five to build, precisely because it doesn't solve the trigger problem at all.

## Recommendation for the from-scratch Bun/TS build

**Start with polling using `users.history.list` + a stored `historyId` cursor (Pipedream's pattern), not `messages.list` + timestamp filtering (n8n/Activepieces' pattern).** Reasoning:

1. **Gmail push notifications (`users.watch()` + Cloud Pub/Sub) are real infrastructure, not just an API call**: they require (a) a GCP project with a Pub/Sub topic, (b) granting Gmail's service account `gmail-api-push@system.gserviceaccount.com` publish rights on that topic (an IAM step outside Gmail's own API), (c) a `watch()` call that **expires after 7 days** and must be proactively renewed (a scheduled job, same shape as an OAuth-refresh-ahead-of-expiry job — see `auth-patterns.md` #4), and (d) your own endpoint to receive Pub/Sub push messages (which then still requires calling `history.list` to get the actual delta — Pub/Sub only tells you "something changed," not what). This is a second full trigger-infrastructure subsystem (topic provisioning, watch-renewal scheduler, push endpoint) on top of whatever polling infra you build anyway — every platform surveyed that offers it (Pipedream, and Composio per docs) treats it as an **opt-in upgrade layered on top of a working polling path**, never a replacement for it. Build polling first; treat Pub/Sub watch as a v2 low-latency option once the polling path and its cursor/dedup logic are solid.
2. **Prefer `historyId`-based delta fetch over timestamp filtering from the start** — it's barely more code than Activepieces' approach (one extra field to track, one extra API method) but avoids the boundary-condition bugs that made n8n's implementation need four separate tuning constants to paper over. Handle the "expired `historyId`" 404 case explicitly (reseed from `getProfile()`), exactly as Pipedream does.
3. **Activepieces' trigger file (`triggers/new-email.ts`) is the best starting shape to adapt**, not copy verbatim: same language (TS), same lean structure (auth + props + store-based cursor + poll function), MIT-licensed. Swap its `after:<timestamp>` query for `history.list({ startHistoryId })` per point 2, and reuse Klavis's `googleapis`-based Gmail client setup and MCP tool-schema pattern (`@modelcontextprotocol/sdk` + `zod` + `zod-to-json-schema`) for the send/read/search/modify/delete action side, since Klavis is the only platform surveyed whose Gmail integration is *already* MCP-native TypeScript.
4. **Auth**: apply the general pattern from `auth-patterns.md` (Composio/Nango-style Auth Config + Connected Account split, proactive refresh) with Gmail's specific OAuth2 scopes (`gmail.readonly`, `gmail.modify`, `gmail.send`/`gmail.compose` as needed) — n8n's and Activepieces' credential files are useful references for the exact scope set and the OAuth-vs-service-account dual auth option worth supporting.
